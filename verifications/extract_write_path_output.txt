## 2. how much of extraction is the write path
-t decodes the whole archive and writes nothing. -x does the same decode
plus the file creation. The difference is the write path, and it is the
ceiling on what parallel writing could ever recover.
-t 解開整個封存但不寫任何檔；-x 是同樣的解碼再加上建檔。兩者之差即為寫檔
路徑的成本，也是平行寫檔所能回收的上限。
corpus     files |   swift -t   swift -x  write path | bsdtar -t bsdtar -x  write path
--------------------------------------------------------------------------------------
few            8 |        75ms       162ms        87ms |      30ms      163ms       133ms
many        8192 |       285ms       438ms       153ms |     169ms      765ms       596ms
## 3. is more than one core actually used
CPU/wall near 1.0 means single-threaded regardless of what -n was set to.
CPU/wall 接近 1.0 表示實際為單執行緒，與 -n 設定無關。

-------------------------------------------------------------

## 4. does --gzip really emit one member per 4 MiB
gzip -l CANNOT answer this: it reads the first header and the trailing 4
bytes only, so its output is always 2 lines no matter how many members
there are. The stream has to be walked member by member.
gzip -l 無法回答這個問題：它只讀第一個 header 與結尾 4 bytes，輸出永遠是
兩行，與成員數無關。必須逐一走訪整個串流。
  mem.bsd.tgz        members=    1  uncompressed/member: min=268,453,376 max=268,453,376
  mem.sw.tgz         members=   65  uncompressed/member: min=51,712 max=4,194,304
4 MiB = 4,194,304. A max of exactly that across many members is the
pigz-style chunking working as documented.
4 MiB = 4,194,304。多個成員的最大值正好是這個數字，即代表 pigz 式分塊如
文件所述正常運作。
