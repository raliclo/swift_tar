# PGO 逐函式計數,Linux,2026-09-06 / Per-function counts, Linux

**結論:那些 CPU 時間不在 swift_tar 自己的 Swift 程式碼裡。**

解開 160 MB(20 × 8 MB)時,swift_tar 全部被儀器化的區塊加起來只執行了 **21,743 次**。
一個每位元組都要做事的路徑不會長這樣。

**The CPU time is not in swift_tar's own Swift code.** Extracting 160 MB executed 21,743
instrumented counter increments in total. A path doing per-byte work does not look like
that.

---

## 怎麼量的 / Method

選 LLVM PGO 儀器化而非取樣,理由是**計數與機器負載無關**——當時 host 的 load 是 4.63,
其中最大宗是另一個專案的 Android 模擬器(74.7%)。取樣式 profiler 在那種情況下會被污染,
逐函式計數不會:它是確定的。

LLVM PGO instrumentation rather than sampling, because the counts are exact regardless of
contention: the host was at load 4.63, three quarters of it another project's Android
emulator. Sampling would have been contaminated; counting is not.

```zsh
# guest 內,以已入版的建置腳本加一個旗標(diff 恰好一行)
"$SWIFTC" -O -swift-version 6 -profile-generate "${SWIFT_DEFINES[@]}" ...

LLVM_PROFILE_FILE=/tmp/pc/st.profraw ./release/swift_tar -x -f /tmp/pc/a.tar -C /tmp/pc/out
llvm-profdata merge -output=st.profdata st.profraw
llvm-profdata show -topn=25 st.profdata
```

語料 20 × 8 MB 於 tmpfs——即三種形狀中差距最大的那一個(Linux 上 1.46×)。
Corpus: the shape with the largest gap, on tmpfs.

## 判讀 / Reading it

**`readExactly` 在整場只執行 63 次。** 20 個成員、160 MB——它顯然是以大塊讀取,而不是
每 4 KB 呼叫一次。`parseTarNumber` 的 819 次也符合「每個成員的表頭有數個數值欄位」
(819 ÷ 20 ≈ 41),與資料量無關。**沒有任何一個計數隨位元組數成長。**

這與先前在 macOS 量到的一致:user 0.015 秒對 sys 0.146 秒,**sys 是 user 的十倍**。
兩者說的是同一件事——swift_tar 的 Swift 程式碼幾乎不做事,時間在系統呼叫的另一側。

`readExactly` ran 63 times for the whole extraction. Nothing here scales with byte count.
That matches the macOS split of user 0.015 s against sys 0.146 s: the Swift code barely
runs, and the time is on the far side of the syscall boundary.

**這一輪排除的是「swift_tar 自己的 Swift 計算」。** 那是一個候選,現在它出局了。

## 這個方法看不到什麼 / What this method cannot see

**前端儀器化在系統呼叫邊界就停住。** 它數的是被儀器化的區塊執行了幾次,不是時間,
更看不到核心裡發生什麼。既然證據指向的正是那一側,PGO 到此為止——它能告訴我們
「不是這裡」,不能告訴我們「是那裡的什麼」。

Front-end instrumentation stops at the syscall boundary. It counts instrumented regions,
not time, and sees nothing inside the kernel — which is exactly where the evidence points.
It can say "not here"; it cannot say what, over there.

**下一步該量的是系統呼叫本身**:write/read 的**次數與每次的大小**,swift_tar 對 bsdtar。
若 swift_tar 以較小的塊寫入,呼叫次數就會較多,而那正好會產生「user 相近、sys 較高」的
形狀。**這是一個待驗的假設,不是結論**——本節刻意不指名機制,因為 FAQ 那一節已經有三個
機制以「數字不足就先指名」的方式被提出又推翻。

The next thing to measure is the syscalls themselves: the count and size of write/read for
each tool. A smaller write block would produce more calls and exactly the observed shape.
**That is a hypothesis to test, not a conclusion** — this file deliberately names no
mechanism, because three have already been named and overturned in the FAQ's section by
doing so ahead of the numbers.

Guest 內沒有 `strace`、`perf`、`gdb`、`valgrind`(只有 Swift toolchain 附的 `lldb`),
故那次量測需要另找工具或另一台 Linux。
The guest has no strace, perf, gdb or valgrind — only the toolchain's lldb — so that
measurement needs a different tool or a different Linux host.
